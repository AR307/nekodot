# Side Phase 3 账号检查与本地验收

## 已落地

- 注册先使用 SMTP 验证邮箱，再创建正式账号；验证码为 6 位、10 分钟、60 秒重发、最多 5 次尝试，重发废弃旧码。邮箱每小时 5 次、来源 IP 每小时 20 次发送。
- 验证码数据库只存服务端 HMAC 摘要；密码继续使用 argon2id。SMTP 不可用时明确失败，不提供绕过验证的产品模式。
- 密码登录、已有账号补验、密码重置与修改、服务端退出。已有账号保留 userId、节点与历史；未补验不签发新登录凭证。
- 30 天登录会话可以撤销；退出撤销当前会话，密码修改/重置撤销该账号所有会话，并关闭对应业务和屏幕连接、解除设备通知绑定。长连接心跳检查会话到期。
- Web 适配验证码、补验、重置和真正退出；认证过期关闭码 4401 会清除登录态，不再无限重连。

## 本地检查结果

| 场景                                 | 结果与依据                                                                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 原退出只清客户端，复制出的凭证仍有效 | 源码确认旧 JWT 无服务端会话撤销；新增 session。真实 loopback HTTP/WS 验证 logout 后 `/api/me` 为 401，业务连接收到 4401。      |
| 无邮箱证明即可创建正式账号           | 旧 signup 直接创建用户；新流程无码拒绝且数据库不创建用户，实际本地 SMTP 收码后才能创建。                                       |
| 验证码暴力、重发、重放               | 本地 SMTP 旅程验证 5 次错误后正确码仍拒绝、60 秒内重发拒绝、新码可用、消费后不可重用；数据库不含明文码。                       |
| 密码重置后的旧凭证                   | 实际重置后旧 `/api/me` 返回 401；旧账号补验仍使用原 userId。                                                                   |
| 来源 IP 伪造                         | 默认不信任转发头；实测伪造 X-Forwarded-For 仍按连接来源限流。部署只可配置明确可信代理，不设置 `trustProxy=true`。              |
| 不存在邮箱的重置枚举                 | 相同成功响应但不发邮件，不通过响应透露邮箱是否存在；登录错误统一为邮箱或密码错误。未做统计时序结论。                           |
| 跨账号节点、文件、屏幕               | 两个隔离账号的现有路由旅程验证他人节点 RPC、文件转发和屏幕票据拒绝，节点解绑后失效。授权专用接口尚未完成，不声称已审计该接口。 |
| 已连接屏幕退出                       | 实际 loopback 二进制通道中退出后 viewer 和 node 均收到 4401，退出前未使用的票据不能再建立连接。                                |

测试入口：`apps/relay/src/auth.test.ts`、`tunnels.test.ts`、`server.test.ts`、`notifications.test.ts` 及 Edge 注册/私聊/群聊旅程。路由专项测试直接准备已验证账号；完整账号与浏览器注册使用实际 loopback SMTP，不绕过产品验证逻辑。

## 待验收与部署限制

- 用户正在准备外部 SMTP，本轮只验证本地 SMTP 收发；外部真实邮箱、服务商 TLS、投递与退信未通过，不能写作真实外部收码成功。
- 线上 Caddy 可信代理地址和真实来源 IP 仍须部署前核对；没有修改或重启线上服务。
- Flutter 的安全存储与账号界面已编写，尚需原生设备完整旅程，不以 Edge 截图替代。
- 这是已检查边界与可复现问题的记录，不是对整个项目“无漏洞”的保证。
