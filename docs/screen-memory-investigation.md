# 小内存 VPS 屏幕启动调查

2026-11-01；只读检查用户报告的实际故障节点。没有停止其他安装/容器、修改系统配置、清空缓存或绕过 Hermes 屏幕门槛。

## 实际原因

- 物理内存约 1967 MiB，复查时可用 380 MiB；约 1987 MiB 的 swap 已用 1501 MiB。
- 原生 `display.status` 显示依赖已安装、屏幕未运行；blocker 明确为可用内存不足。当前 `bot_desktop.min_free_memory_mb` 要求 1536 MiB，可用量只有约 380–452 MiB。
- 这不是 Relay 离线、缺少驱动或客户端唤醒超时。没有找到内核 OOM 记录；不能把既有 SIGKILL 日志直接认定为 OOM。

## 占用分解

项目 systemd cgroup 当前约 500 MiB，记录峰值约 792 MiB。为避免误把共享映射重复计算，另取了 `smaps_rollup` 的 PSS：

| 项目进程       | RSS (MiB) | PSS (MiB) | SwapPss (MiB) |
| -------------- | --------: | --------: | ------------: |
| Node           |        12 |         9 |            45 |
| 原生 gateway   |       258 |       253 |            49 |
| 原生管理 serve |       233 |       228 |            33 |

这是进程瞬时测量，不是运行任意任务时的固定上限。节点还承载其他服务及另一个 Hermes 实例；它们不属于本次可擅自关闭的项目资源。

## 精简方向与边界

1. **主要可研究点是重复的 Python 后端，而非 Flutter 或 Relay。** 当前 gateway + 独立 `hermes serve --isolated` 各有运行时。新原生源码已有 gateway 内的管理 HTTP/WS；但它使用官方私有控制连接获取的单次票据，不能简单换 URL 或把 API_SERVER_KEY 当票据。若后续收敛到该官方通路，应一并验证 profile、管理事件、文件与屏幕，不能直接去掉 serve 让已有能力失效。本轮没有增加 Python 桥、修改 Hermes 核心或部署未经验证的合并方案。
2. 即使完整省下当前独立管理进程的约 228 MiB PSS，也仍远低于 1536 MiB 可用门槛；这不是足以解决本机屏幕的优化。以目前负载，不能承诺 2GB 共享机器稳定运行真实桌面和浏览器。
3. Hermes 已有空闲内存 trim、会话回收和屏幕空闲回收。API 聊天本身按请求建立 agent；盲目压低 gateway agent-cache 数量不能等价减少当前固定 Python 占用。没有为理论优化改写这些原生策略。
4. 降低画面尺寸只能节省少量帧缓冲，不能回收浏览器主要工作集；增加 swap 也不会变成原生检查所需的物理可用内存。本轮没有关闭浏览器沙箱、任意降低资源门槛或强行启动后宣称成功。
5. **实际建议：聊天可继续；屏幕放到更空闲的节点，或使用独占约 4GB 及以上的 VPS，并确认启动前至少约 1.5GB 可用。** 这是基于本机测量的容量建议，不是对所有 4GB 共享机器的保证。若要停用其他服务腾内存，应先明确哪些可停，不能代替用户决定。

## 验收状态

本项完成原因定位、项目占用量化与原生精简路径调查；**没有完成该小内存节点的屏幕成功启动验收，也没有把它写成已修复**。原始日志只保留在私有现场，公开记录不包含 SSH 目标、凭据或个人路径。
